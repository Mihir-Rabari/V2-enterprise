# Remediation roadmap (staging-first; nothing implemented)

Three independent workstreams. Security items are **not** performance work and must not be mixed into performance measurements or the PDP/GTM branch.

## Workstream S: security and correctness (blocks any shared caching and arguably safe release)
Each finding was verified by static inspection of the cited code this session; none was exercised dynamically (no isolated test data/staging).
| ID | Finding | Evidence (file:line) | Confidence | Impact | Remediation direction | Regression tests | Blocks |
|---|---|---|---|---|---|---|---|
| S1 | **Public access to inactive product details**: `getProductByIdService` returns any product by id; only siblings are filtered to ACTIVE | `products/products.service.ts:164-203`; route `products.routes.ts:9` (no auth) | HIGH | Unpublished/discontinued products (name, price, stock, images) readable by anyone with the id; orders cannot be placed for them (order service filters ACTIVE) | Public handler returns 404 unless `status` is ACTIVE (case-insensitive: schema allows `'Active'/'Inactive'` too, `models/Product.ts:75`); admin path for inactive reads | Unit: INACTIVE and `'Inactive'` -> 404 for no token and for customer token; ACTIVE -> 200; admin path -> 200 | shared caching of `/products/:id` |
| S2 | **Client-controlled payment amount**: `create-order` takes `amount` from the body; order creation verifies only the Razorpay signature, never that paid amount equals the DB-computed `total`; the DB total is computed independently | `payments/payments.controller.ts:7-13`, `payments.service.ts:10-12`, `orders/orders.service.ts:92-107,111` | HIGH | Underpayment/overpayment possible by tampering with the client request (a valid payment for any amount unlocks an order of any cart); also makes stale displayed prices chargeable. Requires login (`payments.routes.ts:8` has `protect`), so authenticated users only | Compute amount server-side from cart items (same function as order creation) or store expected amount on the Razorpay order and compare with the fetched payment/order amount at verification; use timing-safe compare for the signature; reject reused payment ids (not checked here) | Unit/integration with mocked Razorpay: tampered amount -> rejected; matching -> ok; replay of payment id -> rejected | any release touching checkout; price caching |
| S3 | **Admin-dependent output on the same URL**: `GET /products?status=ALL|INACTIVE` differs by `Authorization` | `products.controller.ts:11-20,36`; token attached to all requests `frontend/lib/apiClient.ts:47-53`; admin call `frontend/hooks/useAdminData.ts:89` | HIGH | Unsafe for any shared cache (admin response could be served to the public or vice versa); private browser caches are fine | Move admin listing to `/api/v1/admin/products` (`private, no-store`); public route ignores `status`; Cloudflare bypass on `Authorization` | Existing F-03 test plus: public route never returns INACTIVE with admin token | shared caching of `/products` |
| S4 | **Stock decrement targets a non-existent field**: `$inc: { 'variants.$.quantity' }` with filter `'variants.size'`; `Product` schema has top-level `quantity`, no `variants` | `orders/orders.service.ts:129-137`; `models/Product.ts:18,57` | HIGH (static) | Inventory never decreases; no stock check at order time (also not found in `createOrderService`) -> oversell | Decide model (one document per SKU/size as now): atomic `findOneAndUpdate({_id, quantity: {$gte: qty}}, {$inc:{quantity:-qty}})` inside the order flow with rollback on failure | Integration with in-memory/test Mongo: decrement works, concurrent orders cannot oversell, insufficient stock rejected | caching of `quantity` |
| S5 | Categories returned regardless of `status`; `GET /filters/suggestions` writes on read; 500 MB JSON body limit; HTML meta injection not escaped (`app.ts:~150-223`) | `categories.service.ts:4-15`, `filters.service.ts:160-170`, `app.ts:63-64` | MEDIUM-HIGH | information exposure, abuse surface, meta injection (XSS-adjacent) | filter ACTIVE, remove write-on-read, lower body limit, escape meta values | targeted unit tests | edge caching of categories |
